# Filing360 backend — setup & operations

Stack: **Next.js 16** (route handlers, server actions, `proxy.ts`) · **Supabase** (Postgres, Auth, Storage, row-level security) · **Resend** (transactional email, React Email templates).

The site builds and runs without any keys: lead forms return a friendly "call us" fallback, the blog shows an empty state, and emails are skipped. Add the keys below to switch everything on.

---

## 1. Supabase

1. Create a project at [supabase.com](https://supabase.com) (region: **Mumbai `ap-south-1`**).
2. **SQL Editor → New query**, run each file in `supabase/migrations/` **once, in filename order, each as its own query**:
   1. `20261013000000_init.sql` — leads, blog, team
   2. `20261015000000_hr_role.sql` — adds the HR role (must run on its own before the next file)
   3. `20261015000100_careers.sql` — jobs, applications, résumé bucket

   (Or with the CLI: `supabase link --project-ref <ref>` then `supabase db push`.)
3. **Authentication → Sign In / Providers**
   - Turn **off** "Allow new users to sign up". Staff are invited from the admin panel only.
   - Keep Email provider on; "Confirm email" on.
4. **Authentication → URL Configuration**
   - Site URL: your production URL, e.g. `https://filing360.in`
   - Redirect URLs: add `https://filing360.in/auth/confirm`, `https://filing360.vercel.app/auth/confirm`, `https://*-filing360.vercel.app/auth/confirm` (previews) and `http://localhost:3000/auth/confirm`.
5. **Email templates: nothing to do.** Staff invite and password-reset emails are generated by the app (`src/lib/auth/staffAccess.ts`) and sent through Resend, so Supabase's built-in mailer and its dashboard templates aren't used.
6. **Project Settings → API Keys**: copy the URL, publishable key and secret key into the env vars (section 3).

### Create the first admin

```bash
npm run admin:create -- --email you@example.com --name "Your Name"
```

This creates the account (or resets it if it exists), makes it an admin and prints a temporary password once. Sign in at `/admin/login`; you'll be asked to set your own password straight away. Run it again any time you're locked out.

### Adding team members

**Admin → Team → Add / Invite a team member.**

- **Before Resend is set up:** the account is created with a temporary password shown to you once. Share it privately; they must choose their own password on first sign-in. "Reset password" on a member issues a new temporary password the same way.
- **Once `RESEND_API_KEY` is set:** the same form emails a one-time invite link (valid 24 h) instead, "Reset password" emails a reset link, and **Forgot password?** on the login page starts working for everyone.

## 2. Resend

1. Create an account at [resend.com](https://resend.com) → **Domains → Add domain** → add the DNS records (SPF, DKIM, and a DMARC record such as `v=DMARC1; p=none;`) at your DNS provider and wait for "Verified".
2. **API Keys → Create** (permission: "Sending access", restricted to your domain) → `RESEND_API_KEY`.
3. `EMAIL_FROM` must use the verified domain, e.g. `Filing360 <hello@filing360.in>`.

## How it works

### Roles

| Role | Dashboard | Leads | Blog | Careers | Team |
|---|---|---|---|---|---|
| Admin | ✓ | ✓ (incl. delete) | ✓ (incl. delete) | ✓ (incl. delete) | ✓ |
| Sales | ✓ | ✓ | — | — | — |
| Editor | ✓ | — | ✓ | — | — |
| HR | ✓ | — | — | ✓ | — |

Roles live in `public.profiles.role` and are enforced three times: the `proxy.ts` redirect (optimistic), the data access layer (`src/lib/auth/dal.ts`, every page and server action), and Postgres row-level security (final authority). A user with no role, or a deactivated user, cannot sign in.

### Lead pipeline

`LeadForm` → `POST /api/leads` → validation (Zod) → bot checks (honeypot + minimum fill time) → rate limits (per IP and per phone) → de-duplication (same phone with an open lead in the last 30 days updates that lead instead of creating a new one) → insert → response → **after the response**: confirmation email to the customer + alert to the team.

Each lead stores first-touch attribution (UTM tags, `gclid`, landing page, referrer), the page it was submitted from, and a hashed IP. Every status / owner / priority / follow-up change is written to `lead_activities` by a database trigger, so the timeline can't be skipped.

Admin → Leads: filter, search, bulk update, CSV export (≤10,000 rows), assign owners, follow-up reminders, notes / call logs, and email the lead from the panel (logged in `email_logs`).

### Blog

Admin → Blog: rich-text editor (TipTap), image uploads to the `blog-media` storage bucket, categories, tags, SEO panel (score, Google preview, focus keyword, canonical, noindex), autosave every 45 s, revision history (last 50), preview, publish / schedule / unpublish / archive.

- Post HTML is sanitised server-side with an allowlist before it is saved.
- **Scheduling needs no cron**: a scheduled post becomes visible as soon as its time passes; public blog pages revalidate every 5 minutes, and every save revalidates `/blog`, the post, the RSS feed and the sitemap immediately.
- Public URLs: `/blog`, `/blog/page/2`, `/blog/category/gst`, `/blog/<slug>`, `/blog/rss.xml`. Posts carry `BlogPosting` + `BreadcrumbList` JSON-LD, Open Graph and Twitter cards, and appear in `/sitemap.xml` unless marked noindex.

### Careers (jobs + applicant tracking)

Admin → Careers: create a job (draft) → fill in the description, responsibilities, requirements, salary range, closing date and up to 8 screening questions → **Publish**. Jobs can be paused (hidden), closed (page stays up, applications stop, `noindex`) and reopened. A job with applications can't be deleted — close it instead so candidate history is kept.

Public URLs: `/careers` (search + filters, grouped by department) and `/careers/<slug>` (apply form). Open jobs carry `JobPosting` JSON-LD for Google Jobs and are listed in the sitemap.

**Application flow** — built so many people can apply at once without the server handling file bytes:

1. Browser → `POST /api/careers/upload-url` (job must be open, rate-limited) → a one-time **signed upload URL** to `resumes/pending/<uuid>.pdf`.
2. Browser uploads the résumé **directly to Supabase Storage** (progress bar). Bucket limits: 5 MB, PDF/DOC/DOCX only.
3. Browser → `POST /api/careers/apply` → Zod validation → bot checks → rate limits (IP + email) → job still open → screening answers validated → duplicate check (one application per email per job, also enforced by a unique index) → the server reads the file's **magic bytes** to confirm it really is a PDF/Word file → moves it to `applications/<id>/resume.<ext>` → insert → `201` with an `APP-1001`-style reference.
4. After the response: confirmation email to the candidate + alert to `CAREERS_NOTIFY_EMAILS`.
5. A daily Vercel cron (`/api/cron/cleanup-resumes`, 03:00 IST) deletes abandoned uploads older than 24 h.

Admin → Careers → Applications: stage tabs (New → Reviewing → Shortlisted → Interview → Offered → Hired / Rejected / Withdrawn), filters, bulk stage/owner changes, CSV export, 1–5 rating, notes, email templates (interview invite, request details, regret) that can move the stage on send, and a full activity timeline written by a database trigger. Résumés are opened through `/admin/careers/applications/<id>/resume`, which checks the role, logs a "résumé opened" activity and redirects to a **5-minute signed URL** — the bucket itself is private with no public access.

Privacy (DPDP Act): candidates must tick consent; data is used only for hiring; admins can permanently delete an application and its file on request.

**Storage provider**: all résumé storage calls live in `src/lib/careers/resumes.ts`. To move to Cloudflare R2 (S3-compatible, no egress fees) later, re-implement those five functions with presigned S3 URLs — nothing else changes.

### Security notes

- `SUPABASE_SECRET_KEY` is only imported from `server-only` modules.
- `/api/leads` and `/api/careers/*` reject cross-origin posts and oversized bodies.
- Résumés: private bucket, server-issued upload URLs, file-type sniffing, short-lived download links, access logged.
- `/admin` is `noindex`, `no-store`, and disallowed in `robots.txt`; preview deployments disallow all crawling.
- CSV export neutralises spreadsheet formulas.

## Changing the schema

Add a new file in `supabase/migrations/` (never edit an applied migration), run it, then regenerate types:

```bash
npx supabase gen types typescript --project-id <ref> > src/lib/supabase/database.types.ts
```
